# NorthCart: подготовка batch-признаков

## Назначение

Airflow DAG `batch_features` читает PostgreSQL, рассчитывает 17 признаков
для `(customer_id, run_date)` и сохраняет CSV в S3.
Один запуск — один срез. Для обучения и инференса используется один модуль.
Обучение модели и создание целевой переменной не входят в проект.

## Структура

- `dags/batch_features.py` — DAG и взаимодействие с Airflow Connections.
- `dags/calculate_batch_features.py` — загрузка, предобработка, расчёт,
  проверка и локальное сохранение.
- `notebooks/project_NorthCart.ipynb` — EDA, вызовы модуля и проверки.
- `tests/test_features.py` — контрольные примеры без учебной БД.
- `.env.example` — образец локальных параметров без секретов.
- `requirements.txt` — зависимости локальной тетради, Python 3.13.
- `requirements-airflow.txt` — Airflow и PostgreSQL provider, Python 3.12.
- `requirements-dev.txt` — локальные зависимости и pytest.

## Учебная база

- `dbname`: `playground_ds_20260924_846243f49d`.
- `user` из активации: `ds_20260924_846243f49d`.
- Схема: `public`.

Пароль и ключи не включаются в репозиторий.
В PostgreSQL таблицы `customers`, `sessions`, `events`, `orders`.
События связаны с пользователем через `events.session_id = sessions.session_id`.
Денежные признаки вычисляются из `orders.total_usd`.

## Дата и состав пользователей

Единственный параметр запуска DAG — Variable `batch_features_run_date`,
формат `YYYY-MM-DD`, например `2025-08-01`, начало дня UTC.
DAG не использует фиксированную дату когорты.

Каждый срез включает всех пользователей с `signup_date < run_date`,
в том числе без активности. Новые пользователи попадают в поздние срезы.
Окна: `[T − 7 дней, T)` и `[T − 30 дней, T)`.
Данные на верхней границе и позже не используются.
Исходное время без часового пояса трактуется как UTC — рабочее допущение.

**Согласование обучающего и инференсного набора:** выполняется после
расчёта полных срезов, пересечением `customer_id`. Этот шаг показан в
тетради. Полный инференсный файл при этом не изменяется: новые пользователи
сохраняют свои признаки. Отбор общей аудитории не ограничивает универсальный DAG.

## Признаки и порядок колонок

Первыми идут `customer_id`, `run_date`, затем:

| Колонки | Формула |
|---|---|
| `page_view_count_7d`, `page_view_count_30d` | Количество `page_view` |
| `add_to_cart_count_7d`, `add_to_cart_count_30d` | Количество `add_to_cart` |
| `view_to_cart_conversion_7d`, `view_to_cart_conversion_30d` | `add_to_cart / page_view` |
| `cart_to_purchase_conversion_7d`, `cart_to_purchase_conversion_30d` | `purchase / add_to_cart` |
| `unique_products_7d`, `unique_products_30d` | Уникальные непустые `product_id` |
| `avg_session_duration_30d` | Средняя длина сессий в секундах |
| `session_count_7d`, `session_count_30d` | Уникальные сессии по времени начала |
| `days_since_last_purchase` | Полные сутки от последнего заказа до `T` |
| `order_count_30d` | Уникальные заказы |
| `total_spend_30d` | Сумма `total_usd` |
| `avg_order_value_30d` | Средний `total_usd` |

Длительность — от начала сессии до последнего её события до `T`.
В среднее входят сессии, начавшиеся в 30-дневном окне; события раньше
начала сессии для длительности не используются.
Конверсии являются отношениями событий и не ограничиваются единицей.
Давность покупки учитывает всю доступную историю, а не только окно.

## Предобработка и загрузка

- Невалидные даты и отсутствующие обязательные ключи исключаются.
- Дубликаты событий удаляются по `event_id`; других таблиц — по их ключам.
  Сохраняется первая запись; в исходном исследовании конфликтующих повторов не было.
- Пустой `product_id` исключается только из товарного признака.
- Нечисловой/пустой `total_usd` заменяется на `0.0`.
- Счётчики без активности: `0`; вещественные признаки: `0.0`.
- Нулевой знаменатель: `0.0`; нет заказов в истории: давность `−1`.
- Нет событий у сессии: длина `0`.

В DAG SQL-загрузка ограничивает события и заказы последними 30 днями.
Для давности SQL отдельно возвращает `MAX(order_time)` по пользователю
с условием `order_time < T`.
Сессии загружаются из окна плюс более старые сессии, имеющие события
внутри окна: они нужны для связи событий с пользователем, но не входят
в оконные сессионные показатели. Это сохраняет события на границе окна.
Полная история доступна через `full_history=True` только для локального EDA
и проверки эквивалентности.

## Airflow Connections

Настройте **Admin → Connections**.

### PostgreSQL

- Connection ID: `postgres_raw`.
- Connection Type: `Postgres`.
- Host: `<host>` из активации.
- Schema: `playground_ds_20260924_846243f49d` (имя БД).
- Login: `ds_20260924_846243f49d`.
- Password: `<your_password>`.
- Port: `6432`.

Extra:

```json
{"sslmode": "require", "connect_timeout": 15}
```

Модуль также явно требует SSL при создании SQLAlchemy engine.

### S3

- Connection ID: `aws_default`.
- Connection Type: `Amazon Web Services`.
- В данной реализации ключи читаются из Extra; отдельные поля оставляются пустыми.

```json
{
  "bucket": "<bucket_from_activation>",
  "endpoint_url": "https://storage.yandexcloud.net",
  "aws_access_key_id": "<your_access_key>",
  "aws_secret_access_key": "<your_secret>"
}
```

Клиент использует `ru-central1`, `s3v4`, адресацию `path`.

## Запуск и выходные файлы

1. Отправьте файлы в `main` учебного GitLab; дождитесь синхронизации с Airflow.
2. Проверьте отсутствие ошибок импорта `batch_features`.
3. Настройте Connections и **Admin → Variables**:
   `batch_features_run_date = 2025-09-01`.
4. Включите DAG, нажмите Trigger DAG.
5. Дождитесь успеха `build_and_upload_features` и `validate_saved_result`.
6. После завершения измените дату и выполните следующий запуск.

Настройки: `schedule=None`, `catchup=False`, `start_date=2025-01-01`,
`max_active_runs=1`. `start_date` не ограничивает передаваемый `run_date`.
Не меняйте Variable во время активного запуска.

Локальный промежуточный файл:
`/tmp/batch_features/run_date=<дата>/batch_features.csv`.

S3:

```text
run_date=2025-08-01/batch_features.csv
run_date=2025-09-01/batch_features.csv
run_date=2025-10-01/batch_features.csv
run_date=2025-11-01/batch_features.csv
```

Разные даты не перезаписывают друг друга. Повтор той же даты заменяет
файл этого среза. Задача проверки выполняет `HeadObject` и проверяет
ненулевой размер; дополнительное право `HeadBucket` не требуется.

## Локальный запуск

Не устанавливайте Airflow в существующую Anaconda с Python 3.13.
Локальный расчёт и DAG имеют отдельные наборы зависимостей.

Из корня проекта, в локальном окружении Python 3.13:

```bash
python -m pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env` своими параметрами. Он исключён из Git.
Откройте тетрадь в `notebooks/`, выберите это окружение как Kernel и
выполните Restart & Run All. Все импорты находятся в одной ячейке;
тетрадь читает конфигурацию через `python-dotenv` и не выводит секреты.

Для воспроизведения окружения DAG создайте **отдельный Python 3.12 venv**:

```bash
python3.12 -m venv .venv-airflow
source .venv-airflow/bin/activate
python -m pip install -r requirements-airflow.txt
python -m pip check
```

Версии согласованы с официальными constraints Airflow 2.10.5 для Python 3.12:
https://raw.githubusercontent.com/apache/airflow/constraints-2.10.5/constraints-3.12.txt
Это спецификация для установки, а не утверждение о точных версиях
в готовом учебном кластере. Изменять его окружение для запуска проекта не требуется.

## Проверка доработки

Локальные тесты:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
python -m py_compile dags/batch_features.py dags/calculate_batch_features.py
```

Проверяются ранние даты, новые пользователи, границы окон, старые покупки,
нулевые знаменатели, дубликаты, невалидные значения и события в старых сессиях.
SQL-эквивалентность в тестах проверяется на SQLite; PostgreSQL и реальные
подключения необходимо проверить в учебном Airflow.

После обновления кода **повторно** запустите DAG на четырёх датах выше.
Ожидаемые размеры по данным ревью (19 колонок в каждом файле):

| run_date | Ожидаемые строки |
|---|---:|
| 2025-08-01 | 16 992 |
| 2025-09-01 | 17 292 |
| 2025-10-01 | 17 558 |
| 2025-11-01 | 17 846 |

Это ожидаемые значения, а не результаты ещё не выполненных новых прогонов.
Тетрадь сравнивает полную и оконную загрузку на каждой дате.
После успешных прогонов задайте `RUN_S3_CHECK=true` в `.env`, перезапустите
ядро и выполните тетрадь: она сравнит каждый CSV из S3 с локальным расчётом
и отдельно согласует общий набор пользователей для обучения и инференса.
Выводы старой версии очищены; сохраните актуальные результаты перед сдачей.
