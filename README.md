# NorthCart: пайплайн подготовки батч-признаков

Воспроизводимый пайплайн на Apache Airflow для подготовки пользовательских признаков из PostgreSQL и сохранения датированных срезов в S3.

DAG рассчитывает **17 признаков для каждой пары `customer_id` и `run_date`**. Исторические срезы и срезы для инференса формируются одним Python-модулем — меняется только дата расчёта.

## Задача

NorthCart использует модель, прогнозирующую покупку пользователя в ближайшие семь дней. Для её работы нужны агрегированные признаки поведения: просмотры товаров, добавления в корзину, сессии и покупки.

Требовалось реализовать пайплайн, который:

- читает исходные данные из PostgreSQL;
- выполняет предобработку и рассчитывает признаки относительно `run_date`;
- исключает данные из будущего;
- использует одинаковую логику для обучения и инференса;
- сохраняет каждый срез по отдельному пути в S3;
- проверяет корректность таблицы и наличие сохранённого результата.

Обучение модели и формирование целевой переменной не входят в проект.

## Источники данных

Используются четыре таблицы учебной PostgreSQL-базы:

- **customers** — пользователи и дата регистрации;
- **sessions** — пользовательские сессии и время их начала;
- **events** — события внутри сессий;
- **orders** — заказы, время покупки и сумма `total_usd`.

События связываются с пользователем через `session_id` таблицы `sessions`. Денежные показатели рассчитываются по таблице `orders`.

Доступ к базе и объектному хранилищу предоставлялся Яндекс Практикумом. Исходные данные и секреты в репозиторий не включены. Для запуска нужны собственные подключения и таблицы с соответствующей структурой.

## Дата среза и состав пользователей

Параметр запуска — Airflow Variable **`batch_features_run_date`**.

Формат: `YYYY-MM-DD`, например `2025-09-01`. Дата интерпретируется как начало дня UTC.

Для даты `T` используются окна:

- оперативное: `[T − 7 дней, T)`;
- стабилизированное: `[T − 30 дней, T)`.

События, сессии и заказы с временем на верхней границе или позже не участвуют в расчёте. Исходные временные значения без часового пояса трактуются как UTC — рабочее допущение проекта.

Каждый срез включает пользователей с `signup_date < T`, в том числе без активности. Состав пользователей пересчитывается при каждом запуске: новые пользователи появляются в более поздних срезах.

Если для обучения и инференса нужен общий набор пользователей, он формируется после расчёта полных срезов через пересечение `customer_id`. Этот шаг показан в тетради. Полный инференсный файл сохраняет новых пользователей.

## Рассчитываемые признаки

Первые две колонки — `customer_id` и `run_date`. Далее следуют:

| Колонки | Расчёт |
|---|---|
| `page_view_count_7d`, `page_view_count_30d` | Количество событий `page_view` |
| `add_to_cart_count_7d`, `add_to_cart_count_30d` | Количество событий `add_to_cart` |
| `view_to_cart_conversion_7d`, `view_to_cart_conversion_30d` | `add_to_cart / page_view` |
| `cart_to_purchase_conversion_7d`, `cart_to_purchase_conversion_30d` | `purchase / add_to_cart` |
| `unique_products_7d`, `unique_products_30d` | Число уникальных непустых `product_id` |
| `avg_session_duration_30d` | Средняя длительность сессий в секундах |
| `session_count_7d`, `session_count_30d` | Число уникальных сессий по времени начала |
| `days_since_last_purchase` | Полные сутки от последнего заказа до `T` |
| `order_count_30d` | Число уникальных заказов |
| `total_spend_30d` | Сумма `total_usd` |
| `avg_order_value_30d` | Средний `total_usd` |

Длительность сессии определяется как время от её начала до последнего события до `T`. В среднее входят сессии, начавшиеся в 30-дневном окне. События раньше начала сессии при расчёте длительности исключаются.

Конверсии являются отношениями количества событий и могут превышать единицу. Давность последней покупки учитывает всю доступную историю заказов.

## Предобработка

- Невалидные даты и отсутствующие обязательные ключи исключаются.
- Дубликаты событий удаляются по `event_id`, остальных таблиц — по соответствующим ключам.
- При дублировании ключа сохраняется первая запись; конфликтующих повторов в исходном исследовании не обнаружено.
- Пустой `product_id` исключается только из расчёта уникальных товаров.
- Нечисловой или пустой `total_usd` заменяется на `0.0`.
- Счётчики без активности заполняются `0`, вещественные признаки — `0.0`.
- При нулевом знаменателе конверсия равна `0.0`.
- Для пользователя без заказов давность покупки равна `−1`.
- Сессия без доступных событий имеет длительность `0`.

## Оптимизация загрузки

Для расчёта DAG загружает события и заказы только за последние 30 дней.

Давность последней покупки рассчитывается по отдельному SQL-агрегату `MAX(order_time)` с условием `order_time < T`. Загружать всю историю заказов в память не требуется.

Сессии загружаются из 30-дневного окна, а также более ранние сессии с событиями внутри окна. Старые сессии нужны для связи событий с пользователями, но не входят в оконные сессионные показатели.

Режим `full_history=True` используется в тетради для исследования и проверки эквивалентности полной и оконной загрузки.

## DAG

DAG состоит из двух последовательных задач:

1. **`build_and_upload_features`** — чтение даты, загрузка данных, расчёт и проверка признаков, сохранение CSV, загрузка в S3.
2. **`validate_saved_result`** — проверка числа строк и наличия непустого объекта в S3.

Настройки:

- `schedule=None` — ручной запуск;
- `catchup=False`;
- `start_date=2025-01-01`;
- `max_active_runs=1`.

`start_date` не ограничивает дату среза, передаваемую через Variable. Не следует менять `batch_features_run_date` во время активного запуска.

## Настройка Airflow

### PostgreSQL Connection

В **Admin → Connections** создайте подключение:

| Поле | Значение |
|---|---|
| Connection ID | `postgres_raw` |
| Connection Type | `Postgres` |
| Host | `<your_host>` |
| Schema | `<your_database_name>` |
| Login | `<your_username>` |
| Password | `<your_password>` |
| Port | `6432` для учебного подключения |

Для другой базы укажите её фактический порт. Исходные таблицы ожидаются в схеме `public`.

Extra:

```json
{
  "sslmode": "require",
  "connect_timeout": 15
}
```

Модуль также явно включает SSL при создании SQLAlchemy engine.

### S3 Connection

Создайте второе подключение:

- Connection ID: `aws_default`;
- Connection Type: `Amazon Web Services`;
- в данной реализации параметры читаются из Extra, отдельные поля ключей оставляются пустыми.

Extra:

```json
{
  "bucket": "<your_bucket>",
  "endpoint_url": "https://storage.yandexcloud.net",
  "aws_access_key_id": "<your_access_key>",
  "aws_secret_access_key": "<your_secret_key>"
}
```

Клиент настроен для Yandex Object Storage: регион `ru-central1`, подпись `s3v4`, адресация `path`. Для другого хранилища потребуется адаптировать настройки клиента.

### Variable

В **Admin → Variables** добавьте:

```text
Key: batch_features_run_date
Value: 2025-09-01
```

## Запуск и сохранение результатов

1. Разместите файлы из `dags/` в каталоге DAG вашего Airflow.
2. Убедитесь, что DAG `batch_features` появился без ошибок импорта.
3. Настройте Connections и Variable.
4. Включите DAG и нажмите **Trigger DAG**.
5. Дождитесь успешного завершения обеих задач.
6. Для следующего среза измените Variable после завершения предыдущего запуска.

В учебном окружении доставка кода в Airflow выполнялась синхронизацией с GitLab. Этот GitHub-репозиторий хранит портфолио проекта; автоматическая доставка из него не настроена.

Промежуточный локальный файл:

```text
/tmp/batch_features/run_date=<дата>/batch_features.csv
```

Путь в S3:

```text
s3://<bucket>/run_date=<дата>/batch_features.csv
```

Разные даты сохраняются раздельно. Повторный расчёт той же даты заменяет файл соответствующего среза.

После загрузки задача валидации проверяет объект через `HeadObject`. Дополнительная проверка доступа через `HeadBucket` не используется.

## Локальный запуск

Для тетради и локального расчёта используется Python 3.13.

Из корня проекта:

```bash
python -m pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env` своими параметрами. Файл исключён из Git; секреты в `.env.example` не указываются.

Откройте `notebooks/project_NorthCart.ipynb`, выберите нужное окружение как Kernel и выполните **Restart & Run All**.

Конфигурация читается через `python-dotenv`. Все импорты собраны в одной ячейке.

### Отдельное окружение Airflow

Для Airflow используется Python 3.12. Не устанавливайте его зависимости в локальное окружение проекта с Python 3.13.

```bash
python3.12 -m venv .venv-airflow
source .venv-airflow/bin/activate
python -m pip install -r requirements-airflow.txt
python -m pip check
```

Эти команды устанавливают зависимости; для работы локального Airflow дополнительно потребуется настроить сам сервис.

Зависимости согласованы с [официальными constraints Airflow 2.10.5 для Python 3.12](https://raw.githubusercontent.com/apache/airflow/constraints-2.10.5/constraints-3.12.txt). Они описывают воспроизводимое окружение установки, а не точный состав готового учебного кластера.

## Проверка корректности

Установка тестовых зависимостей и запуск проверок:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
python -m py_compile dags/batch_features.py dags/calculate_batch_features.py
```

Тесты проверяют:

- ранние даты среза и появление новых пользователей;
- границы временных окон;
- давность покупки за пределами 30-дневного окна;
- нулевые знаменатели и отсутствие активности;
- дубликаты и невалидные значения;
- события внутри окна, относящиеся к старым сессиям.

SQL-эквивалентность в автоматических тестах проверяется на SQLite. Проверка PostgreSQL, Airflow Connections и загрузки в S3 выполняется отдельно в рабочем окружении.

Тетрадь сравнивает результаты полной и оконной загрузки. Для сверки сохранённых CSV с локальным расчётом установите в `.env`:

```text
RUN_S3_CHECK=true
```

Затем перезапустите ядро и выполните тетрадь.

## Результат

Реализован пайплайн с единой логикой расчёта исторических и инференсных срезов:

- 17 признаков и 2 служебные колонки;
- одна строка на пару `customer_id` и `run_date`;
- фильтрация данных относительно даты среза;
- динамический состав пользователей;
- ограниченная оконная загрузка вместо переноса всей истории;
- отдельные файлы в S3 для каждой даты;

## Ограничения

- Временные поля без часового пояса интерпретируются как UTC.
- Фильтрация опирается на время события. При наличии поздно поступающих данных для строгой исторической воспроизводимости потребуется учитывать также время их поступления.
- Повторный расчёт воспроизводим при неизменных исходных данных. Версионирование исходной базы и выходных файлов не реализовано.
- Проверка объекта в DAG подтверждает наличие непустого файла; подробная сверка содержимого выполняется в тетради.
- Обучение модели, скоринг и мониторинг её качества находятся за пределами проекта.
